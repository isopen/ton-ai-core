# DurevCode

DurevCode agent: streams an opencode session (thinking summaries, tool calls, output, files, tokens) to Telegram and sends a final summary when the task goes idle.

Built on `@ton-ai/core` + `@ton-ai/opencode` 0.1.0 + `@ton-ai/telegram-bot-api` 0.2.0. Session metadata comes from the local opencode server API (`opencode serve`); message content falls back to the opencode SQLite database in read-only mode when the server has no projection for a session — no opencode modifications required.

## Run

1. Install OpenCode v2:

```sh
curl -fsSL https://opencode.ai/v2/install | bash
```

2. The opencode server does not need to be started manually — the bot starts it
   automatically (`opencode serve --port 4096` when the server is unreachable,
   `OPENCODE_AUTO_SERVE=1`) and stops its own server instance on shutdown. Set
   `OPENCODE_AUTO_SERVE=0` only if you manage the server yourself.

3. Build the project:

```sh
make rebuild-durevcode
```

4. Start the bot:

```sh
cd agents/durevcode
cp .env.example .env  # fill in TELEGRAM_BOT_API_TOKEN and DUREVCODE_CHAT_ID
npm start
```

`.env` in this directory is loaded automatically (real env vars take
precedence); or export the variables inline:

```sh
TELEGRAM_BOT_API_TOKEN=<token> DUREVCODE_CHAT_ID=<chat_id> npm start --prefix agents/durevcode
```

## How it works

1. The `@ton-ai/opencode` plugin lists sessions via `GET /api/session` and reads content via `GET /api/session/{id}/message`, falling back to read-only `opencode.db` (`session` / `part` / `todo` tables) for sessions owned by another process.
2. Parts map to agent events: assistant `text`, `tool` calls with short argument summaries, `patch` file lists. Provider-encrypted `reasoning` parts carry no visible text and are skipped by design.
3. `agent.ts` streams one Telegram message per batch of new events, mirroring the opencode console: plan checklist, tool calls with outputs, replies, files. After `idleSec` without new events (and at least one tool call), the agent sends a final summary: duration, tool count, tokens in/out, cost, changed files, last answer.
4. Each topic keeps a pinned Context message (`tokens used / limit (%)`, in/out/reasoning, cost), edited in place as tokens are spent. The context limit comes from `GET /api/model` and is cached for one hour.

## Session separation

Each watched session gets its own Telegram status message (titled by session), its own event cursor, counters and idle timer — parallel sessions never mix. Selection per poll tick:

- `DUREVCODE_SESSION_IDS` (or legacy `DUREVCODE_SESSION_ID`) → exactly those sessions; a typo fails fast at startup;
- otherwise → up to `DUREVCODE_MAX_SESSIONS` latest sessions in `DUREVCODE_DIR`; new sessions attach automatically.

`DUREVCODE_MAX_SESSIONS` is a hard limit on the watched set, not just the pick window: every tick trims the watched set back to the limit (finalized sessions unload first, then stale-empty ones, then the least recently active; sessions that wait on the user — queued prompt, permission, question — or are mid-tick are never torn down). The session the user is actually interacting with is protected too: a recently landed prompt (5 minutes) or a just-finalized turn (2 minutes) keeps its watch slot even through long thinking silences and even outside the auto-pick window, so a conversation cannot fall silent mid-run just because other sessions bubbled up. A message in a known-but-unwatched topic rebinds the persisted session instead of spawning a new one, displacing nothing until the trim finds room; only truly unknown topics create sessions. A used-again topic rebinds its persisted session, and the trim evicts the least active watched session to restore the limit.

## Threads

With `DUREVCODE_USE_THREADS=1` (default) every attached session gets its own forum topic (`📡 <title> · <id>`); status and summary messages go inside via `message_thread_id`. The session→topic mapping is persisted (`DUREVCODE_STATE_PATH`), so restarts reuse the same topics instead of creating new ones — and editing of the same status message continues. The mapping file is written atomically (temp file + rename), so a kill or a crash during a save can never truncate it and lose the bindings. If a topic was deleted manually, the session is considered deleted with it: the agent never recreates the topic, it unwatches the session, drops its persisted binding and deletes the session in opencode (`DELETE /api/session/{id}`). A merely **closed** topic is treated differently: `TOPIC_CLOSED` errors never delete the session or the binding — delivery retries until the topic is reopened (one warning per topic per half hour, and the probe/typing failures are logged quietly). Telegram Bot API sends no event when a forum topic is deleted, so the agent probes every watched topic with an invisible `typing` chat action once per 5 minutes; the probe raises `message thread not found` and the session is dropped right away, without waiting for a restart. The deletion is only logged — the notice cannot be delivered anywhere, since posting into General is forbidden. Deleted ids stay suppressed in auto-pick across restarts too, because the tombstone list is persisted in the state file: while opencode still lists a deleted session from its own server cache, the agent never re-attaches it and never creates a duplicate topic for the same session. A session deleted in opencode itself is skipped quietly after three empty reads (log only, no Telegram notice), and its persisted binding is dropped so the topic can be reused. Persisted topic bindings of sessions that no longer exist in opencode are pruned (after two consecutive missed reads, so a transiently inconsistent server cannot wipe bindings) so their titles can be reused. Write in a fresh topic to start a new session. Topics are never closed by the agent, so sending keeps working. Requires a forum supergroup with topic-management rights — otherwise the agent logs a warning once and falls back to plain messages for the whole run. The bot also needs the Pin Messages (`can_pin_messages`) admin right, otherwise the Context message is sent but never pinned on top (watch for `Durevcode context pin failed` in logs; the agent re-tries the pin on every restart). Set `DUREVCODE_USE_THREADS=0` to skip topics entirely.

The stop control (`Running · tap Stop`) is persisted, so a restart keeps editing the same control message instead of posting a duplicate one. Typing indicators and topic probes share one rolling per-minute chat budget (`14` actions), so a burst of active sessions can no longer trip Telegram flood control — chat actions are dropped first, real content always has room, and a probe skipped for lack of budget is not marked as done and simply re-runs on a later tick. Inbound messages are processed one at a time, so the update backlog replayed after a restart no longer opens a herd of concurrent prompt pumps.

Duplicate topics are impossible for a session that is already in the forum: beside the session→topic binding, the state file keeps a surviving tag map (`topics`) — the short session-id tag embedded in every topic name (`… · <tag>`) mapped to its topic id. If a binding is lost (state reset, transient API failure), the agent reuses the existing topic from the tag map on attach and rebinding instead of creating a second one. A message written into a topic with no binding revives the session remembered for that topic (opencode lookup by id) rather than starting a new one; a new session is created only when the topic never belonged to a live session. Tombstoned (deleted-with-topic) sessions are never resurrected through the tag map. The map is rebuilt on load from the persisted bindings (old-format state files too), so a restart immediately knows every bound session's existing topic. A topic is declared deleted — and the session behind it dropped — only after two consecutive topic-gone signals (probe, delivery or typing); anything successful in between resets the counter. If opencode's `deleteSession` fails (for example the session is busy), the binding and the surviving topic link are restored, so the next attach reuses the same topic instead of creating a duplicate one.

## Forum control

Write in a session topic and opencode executes it: the message text becomes a session prompt (`POST /api/session/{id}/prompt`), progress streams back into the same topic. Create a new forum topic yourself and write the task there — the agent creates a fresh opencode session for it (`POST /api/session`), binds the topic to it and sends your text as the first prompt. Details:

- only topic messages populate topics (General is ignored) and bot's own messages are skipped; a message without a topic in a non-forum chat does not get dropped — it opens the plain chat lane (see «Plain chat» below);
- `DUREVCODE_ALLOWED_USERS` restricts who can drive sessions (empty = everyone; denied users are ignored silently);
- a prompt sent while the session is busy is queued per session (max 5, oldest drops) and sent when the session frees up, with a `⏳` notice;
- answers quote the question and leave the author's face to the quote: the agent's content messages (answer text and the final summary) are sent as Telegram replies to the message of the prompt author they close, with no name stamped into the answer body — Telegram already renders that author's name in the quote header — attribution is bound by event time (each event carries the attribution of the last prompt sent before the event was created, and that attribution only activates once the prompt's own part lands in the store — a prompt posted mid-turn stays pending and cannot steal a running turn's events onto a later author), so queued prompts from different people and interleaved turns keep their own author, making it visible whose task each message closes in a multi-user history (service cards — Stop control, permission/question cards, status edits — stay neutral); prompts that reach the session from outside Telegram (typed into a local opencode TUI or CLI against the same store) produce a neutral answer without a reply target; every bot message is delivered silently (`disable_notification` on every send — answers, service cards, error notices and the WHIP nudge alike), so the quote arrives without triggering a Telegram push sound; `DUREVCODE_LEAD_MENTION=0` strips the `@username` from the answer lead (an on-by-default colored protocol mention, `tg://user?id=` link) and `DUREVCODE_QUOTE_REPLIES=0` posts answers without the reply quote — both flags off keep a muted chat fully quiet, since neither a mention nor a quote nudges it;
- permission requests raised by tools are posted into the topic; reply `/allow` or `/deny` to that message to decide (`once` / `reject`);
- when the agent asks a question mid-task, the topic gets a card with option buttons — one button per option, a check mark rides the picked ones; a single-choice question submits on the first tap, a multi-choice one toggles picks and waits for the `Done` row, and several questions stack as extra button rows with a per-question `Done` counter; the answered card is rewritten into a resolved summary naming the picked labels; voice replies to a single-question card pick an option or land as free text (see «Voice»); `DUREVCODE_NATIVE_QUESTIONS=1` swaps the card for a native Telegram poll whenever the request fits one — a single question with 2–10 unique options (labels up to 100 chars, the question up to 300) posts as an anonymous poll (voter names are never shown), radio buttons for single-choice and checkboxes (`allows multiple answers`) for multi-choice, silently into the session topic, with a `✅ Finish vote` button riding the poll (Telegram shows one keyboard to everyone, but a press from anyone but the prompt author is refused with a notice; turns started outside Telegram carry no author, so any gated member can finish) — closing the vote reads the final per-option counts, a strict majority wins for single-choice, a tie lands as a free-text answer listing the tied options with their counts, and a checkbox poll collects every voted option; finishing a poll with no votes simply closes it — nothing is re-sent and the question is answered with a `Poll closed — no votes cast.` notice so the run keeps going; the resolved summary posts next to the closed poll, and the poll id, labels and finish token persist across restarts so the button keeps working after one; requests that do not fit (several questions, fewer than 2 or more than 10 options, an empty question) keep the inline card, and a rate-limited poll send retries on the next poll tick;
- `DUREVCODE_ANSWER_FANOUT=1` deduplicates identical work: when a prompt is already running (in another topic or the same one), a same-text prompt (normalized comparison) is held and its author sees a waiting note; the finished answer is posted once — with `DUREVCODE_LEAD_MENTION=1` it is a single message in the primary author's topic colored-mentioning every waiting author and quoting only the primary prompt, with `DUREVCODE_LEAD_MENTION=0` it falls apart into per-topic copies, each quoting its own author; the first follow-up or fresh prompt in a waiting topic dissolves the fan-out and runs that topic's own delivery, and once the shared answer is posted the held duplicates are dropped without ever starting their own sessions;
- the agent can close the task itself: an answer that ends with a standalone `/stop` line (optionally `/stop@bot`, on its own line) is split there — the answer is posted, then the command arrives as its own message, then the session goes through the same stop as the typed command and `Stopped, send the task again.` lands last. A `/stop` mentioned inside the prose is ordinary text.
- text documents are inlined into the prompt (up to 20000 chars, binaries declined); captions are prepended.
- photos, GIFs, videos and PDF/video documents are downloaded into `<DUREVCODE_DIR>/tmp/.agent-inbox/` (max 20 MB, filename sanitized, inbox capped at 200 files) and passed to opencode as a `[file name] saved to <path>` reference for the read tool; captions are prepended.
- `/stop`, `/mode`, `/models` (or its `/model` alias), `/status`, `/settings` and `/langs` (alias `/lang`) work as slash commands; a handled typed command bubble always stays in the chat — the bot never deletes commands (the same holds for the answered `/allow`//`/deny` bubbles), so subagent answers keep quoting their command messages and the history keeps its context (plain texts and spoken phrases are never deleted either); the status card renders session tag, model and effort, build/plan, context occupancy with the limit percent, running/idle with the last event age, the prompt queue depth, spend, rate-limit cooldown, the whisper setup and the last voice latency, with a `Refresh` button that re-renders the same message. The mode card carries a third row, `Watch only · on/off`, that toggles plain mode in place (`mode:observer` callback, the override is stored for the card's own scope — the topic or chat the card lives in — and applies on restart); the mode, model and status cards also open by short spoken phrases containing the root words (up to 5 words) — `модел*`/`model*` roots (whisper punctuation stripped: `список моделей.` works) for the model card, `режим*`/`mode*` roots for the mode card, `статус`/`status`/`состоян` roots for the status card — without starting a session run; pending `/allow`-`/deny` and question-card answers always win over these triggers. `/mode`, `/models`, `/settings` and `/langs` — typed, spoken and every tap on those cards (`mode:*`, `model:*`, `modelvariant:*`, `set:*`, `lang:*`) — are restricted to forum admins (`creator`/`administrator` via `getChatMember`, cached for 5 minutes, `allowedUsers` always pass) and everyone else gets a decline notice; `/status` and stop stay open to everyone.
- `/sessions` (spoken `сесси*`, admin-gated) lists every watched session: state mark (`running`/`idle`), topic title, token occupancy (`used` from the last assistant snapshot or the session lifetime total) and spend, sorted running-first; tapping a row (`session:<id>` callback, admin-gated) pulls that session's full status card fresh into the current topic without switching anything — in the plain chat lane the same rows include every available session (not just watched ones) and a tap switches the lane binding to the tapped session instead (see «Plain chat» below).
- spoken stop, model pick and continuation voice over the same pipeline: a transcript whose first or second token is `стоп`/`stop` stops the run like the typed command (the residue of the phrase is dropped, and typed `стоп …` works the same way — but a `стоп` typed as a reply to a pending question card answers it instead); while a model card is open the transcript picks a model by position (`первый`, `номер два`, `поставь модель номер два`, digits 1–19, model name with a `поставь`/`выбери` anchor and a 4+ letter latin prefix) and confirms in chat, while a `первый` without an open card stays a normal prompt; a transcript starting with `продолж*` re-queues the session's last task (`Продолжай` while work is still running falls through as a plain prompt) and voice replies to pending permission cards decide them (`да`/`нет`/`ок`/`хорошо` allow once, `запрети`/`отмена` deny) while voice replies to single-question cards pick the option (`нет` → `Нет, стоп`, `первый` → the first option) or land as the free-text answer.
- `DUREVCODE_WATCH_ONLY=1` turns the bot into an observer: inbound messages are only shown as ordinary chat text — typed prompts, media collections and new-topic session binding are all skipped and the opencode sessions are never prompted; slash commands (`/stop`, `/mode`, `/models`, `/status`, `/settings`) still work so the mode can be turned off from chat, and answers for runs started outside Telegram keep streaming into their topics as usual. Voice messages still get their whisper transcript posted (without prompting), and the `/settings` card and the `/mode` card bottom row toggle `Watch only` live (an override survives restarts). `DUREVCODE_PLAIN_MODE=1` still works as a legacy alias when the new name is absent.
- voice messages are transcribed with whisper.cpp when `DUREVCODE_WHISPER_ENABLED=1` (compiled binary in `DUREVCODE_WHISPER_BIN`, GGML model in `DUREVCODE_WHISPER_MODEL`, CPU by default with `DUREVCODE_WHISPER_GPU=1` for a CUDA build; ffmpeg converts the Telegram OGG and all sends stay silent); for near-instant transcriptions point `DUREVCODE_WHISPER_SERVER_URL=http://127.0.0.1:8178` at the resident `whisper-server` (same whisper.cpp build) — the model stays loaded and the agent POSTs the audio there instead of spawning a fresh CLI per voice; when the URL does not answer the agent starts the server itself (`DUREVCODE_WHISPER_AUTO_SERVE=0` disables, `DUREVCODE_WHISPER_SERVER_BIN` overrides the default binary placed next to `DUREVCODE_WHISPER_BIN`, per-request log lands in `whisper-server.log` next to the model; the spawned server is resident and outlives agent restarts); when the server is down the transcription falls back to the CLI spawn path; the decoded text is posted into the topic as a reply to the voice and runs as the session prompt, unless it matches a short spoken card command; with the flag off (or on a failed transcription) the bot replies with a notice — video notes, audio and stickers still can't be parsed.
- the voice phrase `настрой*`/`settings` (up to 5 words) opens the settings card with the spoken-card pipeline, and `/settings` opens it typed; the card lists twelve live settings — `Watch only`, `@mention leads`, `Reply quotes`, `Finish notices`, `Shared answers`, `Subagent users`, `New topics`, `Voice transcription`, `Voice language` (`auto`/`ru`/`en`), `Resident whisper server`, `Whisper threads` (4/8/12/16) and `Two columns` (scoped — on puts two buttons per row on the settings card, off keeps one button per row, the default since labels never fit two per row across languages; toggling it only refreshes the captions and keeps the current row layout, the new layout is built on the next `/settings`) — each row is a button that cycles its value in place (`set:*` callbacks), every button sits on its own row unless the `Two columns` row is switched on for the scope, the last row is `Reset all` which returns the current scope back to the `.env` baseline captured at startup; dots echo like `Watch only: on`; the two language rows have their own `/langs` card (typed `/langs`, `/lang` alias, admin-gated like the settings card); the bot registers its own command menu at startup via `setMyCommands` (`/stop`, `/status`, `/mode`, `/models`, `/settings`, `/langs` — the description hints the `/lang` alias, `/subagent <task>`, `/sessions`, `/help`) and pins the same list to every managed chat with a chat scope, so the menu shows up in those chats even when the default scope is overridden or cached, the menu descriptions follow the bot language while `/help` replies with a localized command overview in the scope's language: the card text lists the two items with their current values — `Bot language` (`en`/`ru`/`zh`/`hi`, bot-wide, switches every bot text live) and `Chat language` (`bot`/`en`/`ru`/`zh`/`hi`, scoped — `bot` follows the bot language) — and under each item a row of one-tap buttons shows every language as a short code (`EN`/`RU`/`ZH`/`HI`), the section labels (🤖 bot language, 💬 chat language) live in the card text above the keyboard, are not clickable and name their button row (top row = bot language, bottom row = chat language), the active option carries a check mark (the chat row shows none while it follows the bot language); a tap sets the picked language and refreshes the card in place (`lang:bot:<code>`/`lang:chat:<code>` callbacks, the legacy `lang:bot`/`lang:chat` cycles still work, a scoped `Reset all` on the settings card returns the chat language to the bot baseline); an explicitly picked `Chat language` also directs the model's reasoning and answers — a language directive rides with every submitted prompt (the main turn, the CLI fallback and parallel subagent runs), so the reasoning inside the `Thinking`/`Thought` bubbles and the replies stay in the picked language no matter what language the user writes in, while with the `bot` baseline the model keeps mirroring the user's own language; the appended directive never surfaces — the opencode session echo is matched against the original prompt text so `Reply quotes` and `@mention leads` keep binding (and a directive echo is never mirrored back into the chat), while any directive line the model repeats inside its answer is stripped before rendering; the live `Thinking`/`Thought` reasoning headers render in the scope's language too (as does the `Plan N/M` header of todo blocks); **settings apply to the scope they were pressed in** — a forum topic keeps its own overrides (`settingsScopes` keyed `t<chatId>:<threadId>`), a non-forum chat or the bot chat keeps its own (`c<chatId>`), other topics and chats stay on the baseline, and every text the bot renders in a scope — cards, questions, notices, polls, even finish/stopped notes from parallel subagent runs — uses that scope's `Chat language`, while `Bot language`, `Resident whisper server` and `Whisper threads` stay bot-wide infrastructure; every value mirrors its env variable (`DUREVCODE_LANG`, `DUREVCODE_CHAT_LANG`, `DUREVCODE_WATCH_ONLY`, `DUREVCODE_LEAD_MENTION`, `DUREVCODE_QUOTE_REPLIES`, `DUREVCODE_AUTO_FINISH`, `DUREVCODE_ANSWER_FANOUT`, `DUREVCODE_SUBAGENT_USERS`, `DUREVCODE_NEW_TOPICS`, `DUREVCODE_WHISPER_ENABLED`, `DUREVCODE_WHISPER_LANGUAGE`, `DUREVCODE_WHISPER_AUTO_SERVE`, `DUREVCODE_WHISPER_THREADS`, `DUREVCODE_TWO_COLUMNS`) and takes effect immediately (scoped `Voice language` is applied per transcription instead of patching the plugin); toggles are stored in the persisted state file under `settings` (bot-wide) and `settingsScopes` (per scope, whitelist-sanitized) and are re-applied after every restart, so the card values survive restarts; the pre-scoping flat `settings` overrides keep working as a bot-wide layer and migrate scoped keys into the bot-chat scope on load.

## Plain chat

The bot works in a forum by default, but it also runs in an ordinary chat (private chat or a group where forum topics are off): the chat itself becomes the lane. Two env flags force the decision if needed: `DUREVCODE_FORUM_ENABLED=0` disables topics altogether and starts the bot in the plain mode from the first second, `DUREVCODE_BOT_ENABLED=0` keeps it topics-only by ignoring every topic-less message (setting both to `0` fails the startup — nothing would answer). With the flags at defaults the mode is auto-detected: the first message without `message_thread_id` in the configured chat proves the chat has no topics, and the agent switches to the plain chat mode on the spot:

- the chat binds to ONE opencode session — everything posted in the chat runs on it and all its stream (progress, thinking, answers, files) is delivered straight into the chat with no `message_thread_id` anywhere (no `General` traffic, `Chat action` and context card included);
- the binding resolution order on an inbound message: the persisted binding from the state file (`plainLanes` key, survives restarts; the legacy `plainLane` key migrates to it) → the currently watched session → the first session that resolves (explicit `DUREVCODE_SESSION_ID(S)` first, then the ranked most-recent sessions) → a fresh opencode session created on the spot; `Watch only` never creates sessions and warns once every 10 minutes instead;
- the binding is sticky: once bound, every plain message lands on that exact session even if auto-pick would rank another one higher afterwards; if the bound session disappears from the opencode server, the binding survives two unreadable reads and only then drops (with a warning), so the next message binds a replacement;
- `/sessions` shows every available session (watched plus the resolved ones) and a tap on a row (admin-gated) switches the chat binding to the tapped session with a `Switched to <title>` note — the previous session stays intact on the opencode side but stops streaming into the chat until it is bound again;
- `/status`, `/stop`, `/mode`, `/models`, `/settings`, voices and media all work the same way as in topics; messages that a forum would post into a topic (`is_topic_message` set but no id) are still ignored, and a chat that is actually a forum keeps its topic flow untouched because every topic message carries `message_thread_id` there.

One instance can serve a second, topic-less chat through `DUREVCODE_BOT_CHAT_ID` (any DM or a plain group) while the configured chat keeps working in the forum. Every managed chat carries its own lane in the state file (`plainLanes` maps each chat id to its bound session), so the bindings are independent: the DM lane binds and steers its session, the forum keeps topics for the rest, and `/sessions`, callbacks, `/status` and admin checks work in both chats. When the bot lane takes a session that used to stream into a forum topic, the binding to that topic is released (logged) — from that moment the session streams into the bot chat, and writing in the abandoned topic grows a fresh session for it. In private chats the admin gate treats any member of the bot chat as an admin (there is no administrator role in a DM).

To bring a plain-chat bot back to a forum, clear its chat key in `plainLanes` in the state file (or point the config at another chat) and restart — the agent re-derives the mode from the first inbound message.

## Parallel subagents

A prompt that arrives while the session's turn is still streaming does not have to wait in the queue: when the author differs from the user whose turn is running (or the prompt comes from another managed chat lane), the agent spawns it as a parallel subagent run and both turns proceed side by side. The author id always rides with the queued prompt (not only when it carries a reply or an @mention), so a second user's plain message contends too. Details:

- `DUREVCODE_SUBAGENT_USERS=1` (default) routes a busy-turn prompt from a different allowed user into a fresh child opencode session created in the same project directory; the child inherits the parent's agent and model, so the answer quality matches the configured setup;
- `/subagent <task>` spawns a parallel subagent on demand from the same user (also in the command menu): the task runs in a fresh child session right away no matter who owns the current turn, the answer quotes the command message, and the dispatch notice reports how many tasks run in parallel; without a task the bot explains the syntax; past the parallel cap (or when the spawn fails) the task falls back to the main session queue with a notice — if the session is idle it runs there immediately, otherwise it waits in the queue; `Watch only` scopes ignore the command like any other prompt;
- the subagent streams into its author's lane: in the forum it answers in the author's topic as a reply-quote to their prompt message, in a plain or bot-chat lane — straight into that chat; every send is silent and HTML-escaped like the regular answers;
- subagent messages follow the `Chat language` of the scope where they stream: a parent-lane run uses the topic scope (`t<chatId>:<threadId>`), a side-chat run uses that chat's own scope (`c<chatId>`) — the language directive rides with the subagent task, so the answers, the dispatch notice and the finish/stopped notes render in the picked chat language (with the `bot` baseline the subagent mirrors the task's language);
- a prompt from another managed chat (for example the bot chat while the forum turn runs) is always routed to a subagent, regardless of the author — the lane conflict alone is reason enough;
- up to 8 subagent runs per parent session at once (`SUBAGENT_PARALLEL_CAP`); past the cap the prompt falls back to the ordinary queue with its `⏳` notice;
- the parent session keeps streaming its own turn into its own topic; the stop control (`/stop`, the Stop card button and the spoken `стоп`) only interrupts the subagents of the tapped chat lane — the main session is never stopped by a lane stop, and each stopped run confirms with a `Parallel task stopped.` notice;
- when a subagent finishes, its lane gets a `Subagent finished the task.` notice, and a background prompt on the parent session folds the result into the parent's context — the reply to that prompt is suppressed, so nothing extra lands in the chat;
- session lifecycle follows the runs: a session with live subagents stays `running`, auto-finish waits for them, and the sessions card marks such sessions accordingly; the `Subagent users` row on the `/settings` card toggles the behavior live (persisted like the other settings).
